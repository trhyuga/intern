   const i=document.querySelector('input[name="message"], #commit-summary-input');

## 7. 2026-08-03 の v2.0 改造（済み・すべて本番反映）

### I1 手触りの核
- **グレイズ**: 敵弾を半径 `GRAZE_R=30` 以内でかわすと1発1回カウント。
  `GRAZE_PER_BOMB=70` 回でボム+1（満載なら+500点）。実装は `collisions()` 内。
- **チェイン**: 連続撃破で加算、`CHAIN_HOLD=130`フレーム途切れるとリセット。
  スコア最大 `CHAIN_MAX_MUL=4.0` 倍、クレジット最大1.5倍（`chainScoreMul()` / `chainCredMul()`）。
- **ヒットストップ**: `Game.hitStop` フレーム数ぶん `loop()` で `Game.dt *= 0.07`。
  被弾4 / ボム5 / 大型敵撃破2。
- HUD: 右上にチェイン倍率＋残り時間バー、左下にGRAZE数とボムチャージ。

### I2 武器タイプ3種（`WEAPONS` / `playerFire()`）
強化レベルは共通、**撃ち方だけ**が変わる。格納庫のタブで切替（`Save.data.wpn`）。

| | 弾 | 定数 | 性格 |
|---|---|---|---|
| VANGUARD 扇 | 従来の扇 | rate 1.00 | 近づくほど束が集中して最大火力 |
| LANCE 貫通 | `LANCE_N=[1,1,2,2,3,3,4]` 本 | `LANCE_DMG=2.2` / `LANCE_PIERCE=4` / rate 1.25 | 距離不問、縦に並んだ敵を貫く |
| SWARM 追尾 | 扇と同数の誘導弾 | `SWARM_DMG=0.63` / rate 1.25 | 必中。散開した敵とチェイン稼ぎ |

実測DPS（フル強化・僚機/ホーミング無効）:
近距離ボス V8206 / L8600 / S6686、遠距離 V3417 / L8371 / S6470。
掃討（散開した12体） V176f / L3000f(timeout) / S145f。**三すくみを `t_wpn.cjs` で常時検証**。

貫通は `b.pierce` と `b.seen[uid]` で同じ敵への重複ヒットを防ぐ。敵には `uid`（`ENEMY_UID`）を付与済み。

### I3 難易度＋BOSS RUSH
- `DIFFS`: NORMAL / HARD(クリアで解放) / NIGHTMARE(HARDクリアで解放・シールド自動回復なし)。
  敵HP・敵ダメージ・敵弾速度・クレジット・スコアに倍率。`Save.data.diff` / `clearedDiff`(ビットマスク)。
- **BOSS RUSH**: `RUSH_ORDER` の7体を連戦するタイムアタック。`Game.mode==='rush'`、
  `Director.rush` で分岐、ベストタイムは `Save.data.rushBest`（フレーム）。

### I4 新敵3種＋一時強化アイテム3種
- **プリズム(prism)**: 撃った弾が `split` フラグで52フレーム後に3方向へ割れる。
- **ハンター(hunter)**: `e.hs='dive'/'back'` で急降下と離脱を繰り返す。
- **バルワーク(bulwark)**: `e.guard=1`。**上から来た自機弾（vy<0 かつ横位置が盾の内側）は弾かれる**。
  横か背後から当てる必要がある。
- アイテム **P(POWER 火力×1.6) / R(RAPID 連射×1.7) / T(SLOW 敵弾半速)**、各15秒（`BUFF_DUR`）。
  `Game.buffs` に残りフレーム。効果は `buffPower()` / `buffRapid()` / `buffSlow()`。

### I5 記録
- `Save.data.rec['camp_0'..'camp_2','rush_0'..]` にモード×難易度ごとのベストスコア。
- ゲームオーバー／クリア画面に戦績（最高チェイン・グレイズ・武器・難易度）と BEST / ★NEW RECORD。
- タイトルに難易度別ベスト一覧とラッシュのベストタイム。

## 9. 落とし穴（過去に踏んだもの。同じ轍を踏まない）

0. **毎フレーム作り直しているものを疑う**。`createRadialGradient` / `createLinearGradient` /
   大量の `stroke`・`fillRect` は、動かないなら `makeSprite()` で焼いて `drawImage` する。
   タイトル画面はこれだけで 50ms→22ms になった。
1. **`shadowBlur` は極端に重い**。特に `globalCompositeOperation='lighter'` と併用すると致命的
   （噴射炎を毎フレーム描いて 474ms/frame になった）。→ 炎は `flameSprite()` でオフスクリーンに
   焼いて `drawImage` するだけにした。新しい発光表現を足すときも同じ方針で。
2. **`GLOWQ`** による自動品質調整が `loop()` にある。新しい `ctx.shadowBlur=N` は必ず `gq(N)` を通す。
3. **敵の着地ワープ**: 降下中も `e.t` が進むため、着地した瞬間に `sin(e.t*k)` が飛ぶ。
   → `enterDone(e)` で `e.mt=0` にし、`wobRamp(e)` で振幅を立ち上げること。ボスは `b.moveT`。
4. **演出中の停戦**: `cineLock()` が true の間は `eb()` が弾を出さず、`collisions()` も早期リターン、
   `updateBoss()` も攻撃しない。新しい攻撃経路を足すときはここを通るか確認する。
5. **`eb()` は opt を明示的にコピーしている**。新しい弾プロパティ（`split` `curve` `bloom` など）を
   足したら `eb()` の push オブジェクトにも追加すること。忘れると無言で消える。
6. **iOSでは `audio.volume` が効かない**。ミュートは stop/resume で実装済み。
7. **Playwright はソフトウェア描画**なので絶対値のfpsは当てにならない。**相対比較**で判断する。
8. **`t_smoke2.cjs` は約2分**かかる。他のテストと同じコマンドに混ぜるとタイムアウトする。
9. GitHubの座標クリックは失敗しやすい → `javascript_tool` でボタンを取得してクリック。

## 10. v2.1 / v2.2 で追加したもの（I6〜I9・すべて deployed）

### I6 バランス実測（`t_bal.cjs`）

簡易オートパイロット（敵弾から逃げ、敵の下に潜り、瀕死ならボム）で
強化度3段階 × 難易度3段階 = 9条件を回して計測した結果:

| 強化度 | NORMAL | HARD | NIGHTMARE |
|---|---|---|---|
| 無強化 | 1面で撃墜(105秒) | 1面で撃墜(74秒) | 1面で撃墜(44秒) |
| 中盤 | 3面到達 | 2面到達 | 1面止まり |
| フル | **クリア**（HP残82%） | 3面到達 | 3面で撃墜 |

→ 難易度の勾配は健全と判断。**NORMAL の数値は指示どおり一切変更していない**。
今後バランスを触るときは、まず `node t_bal.cjs` で前後を比較すること。

### I7 演出強化（v2.1）

- `startSlowMo(frames, depth)` / `slowMoScale()` — ヒットストップの「後段」に効く時間スケール。
  開始直後がいちばん遅く、二乗イージングで等速へ戻る。`loop()` で `Game.dt` に掛かる。
  ボス撃破時に `startBossDeath()` から発火（大ボス 120f/0.76、ボス 70f/0.62、中ボス 30f/0.45）。
- `CHAIN_MARKS` = 10/25/50/75/100/150/200、`chainMilestone()` で衝撃波＋フラッシュ＋
  画面ゆれ＋HUDの跳ね（`Game.chainPop`）。50以上はスローモーも入る。
- グレイズ残像 `Game.trail` — グレイズ中だけ3px以上動いた地点を最大12点記録し、
  `drawPlayer()` の先頭で淡い菱形として描く。オーバードライブ中は金色。

### I8 実績メダル（v2.2）

- `ACHIEVEMENTS`（16件）と `unlockAch(id)` の**1関数だけ**が解除の入口。
  重複解除しない・解除時に `Save.save()` とトースト・ジングル（`Sound.achieve()`）。
- 保存先は `Save.data.ach`（累計グレイズ `grazeAll`、武器クリアのビットマスク `wpnClear` も同居）。
  **`Save.reset()` で一緒に消える**（データ初期化の一貫性）。
- 解除フック: `killEnemy()`（初陣・チェイン系）、グレイズ判定（累計）、
  `startBossDeath()`（面ボス・温存・無傷）、`Game.endRun()`（クリア・難易度・武器・RUSH・Zランク）、
  `checkPassiveAch()`（MK-V など状態だけで決まるもの。`drawTitle()` から毎フレーム呼ぶが軽い）。

### I10 ENDLESS モード（v2.3）

本編クリアで解放される3つ目のモード。格納庫を挟まない一発勝負で、
倒されるまでウェーブが続く。**`Game.mode` は `campaign` / `rush` / `endless` の3値**になった。

| 仕組み | 実装 |
|---|---|
| ウェーブ生成 | `endlessWaveSpawn(n)` — 進行度 `t=min(1,n/40)` で数量と敵種プールが増える |
| 台本 | `buildEndlessChunk(from,count)`。`Director.extendEndless()` が終端6手前で20ずつ継ぎ足す |
| 節目 | 8の倍数=中ボス(`emid`) / 24の倍数=ステージボス(`ebos`)。背景と曲は3面ぶんを巡回 |
| 強化 | `endlessHP()`=1+0.135n（敵とボス両方に掛かる）／`endlessDmg()`=1+0.03n（上限2.6） |
| 記録 | `Save.data.endlessBest`（到達ウェーブ）＋ `Save.data.rec['endl_'+難易度]`（スコア） |
| 実績 | `endless25`（不屈）/ `endless50`（際限なし） |

**注意点**:
- ボス撃破時に `Director.onBossDefeated()` が**格納庫に飛ばないよう endless で早期 return** している。
  ここを消すと ENDLESS 中に格納庫へ落ちる。
- `endlessWaveSpawn` は `Game.enemies.length > 34` で追加湧きを止める。
  これが無いと高ウェーブで敵が溜まり続けて描画が死ぬ。
- `Game.endlessWave` は `Director.update()` が毎フレーム `s.n` で上書きする（HUDと倍率の唯一の出どころ）。
- `Save.data.best`（本編の最高到達ステージ）は ENDLESS では**更新しない**。

### I12 描画最適化とスマホ幅での実測（v2.5）

390×844 / DPR2 のスマホ相当で1フレームの実測を取ったところ、**戦闘中は常に60fps上限**
（16.7ms）に張り付いていた一方、**タイトル画面だけ 50ms/frame** かかっていて `GLOWQ` が
自動的に 0.35 まで落ちていた。ゲームで一番最初に見る画面が一番重い状態だった。

原因と対処:

| 原因 | 対処 |
|---|---|
| 地平線グリッド: 発光付きの線を毎フレーム31本 stroke | 動かない放射線＋地平線の光を `gridStaticSprite()` に、光る横線1本を `glowLineSprite()` に焼いて `drawImage` するだけにした |
| CRT感: 走査線266本の fillRect ＋ 放射グラデーションを毎フレーム生成 | `crtOverlay()` に焼き込み。さらに `GLOWQ<1`（＝重い端末）では省略する |
| 星雲: `createRadialGradient` を毎フレーム3回生成 | 色ごとに `nebulaSprite()` へ焼き込み |
| UI の `ctx.shadowBlur=N` が生値で、`GLOWQ` の自動品質調整が効いていなかった | 52か所を `gq(N)` 経由に統一 |

結果 **50ms → 22.5ms**、`GLOWQ` は 1 のまま落ちなくなった（見た目は変えていない）。
焼き込みスプライトは `makeSprite(w,h,draw)` が `SPR_SS=2` 倍で作るので高DPRでもぼやけない。

**注意**: 新しく `ctx.shadowBlur` を書くときは必ず `gq()` を通すこと。
オフスクリーンに1回だけ焼く時（`makeSprite` の中や `flameSprite`）は生値でよい。

あわせてクリア画面で「THANK YOU FOR PLAYING」が BEST 行と重なっていたのを修正
（下段へ移動し、FIN が出る時と BOSS RUSH のタイムが出る時は締めが二重になるので非表示）。

### I14 編隊入場の弧演出＋中ボス差別化の調査（v2.7）

**中ボスの見た目/挙動の差別化**: `drawBoss()`/`bossPatterns()` を確認したところ、
RAZOR(双刃・シアン)／PHANTOM(残像ダイヤ・マゼンタ)／WARDEN(回転二重スクエア・金)は
形状・配色・アニメーションが完全に別デザインで、攻撃パターンも
壁抜け／ダッシュ+リング／加速弾雨+十字+薙ぎ払い、と三者三様になっていた。
スクリーンショットで確認済み。**既存で十分に差別化されているため、追加作業なし。**

**編隊入場の弧演出**: `formationRow()` で組む雑魚編隊が、真上から直線で降りてくる
だけだったのを、左右交互に少しオフセットした位置（±90px）から弧を描いて合流する
ように変更した（元々の企画書にあった「Galaga風の編隊入場」が未実装だったもの）。

```js
// formationRow(): 各機を slotX±90px の位置から spawn し、
// updateEnemy() の先頭で e.arcFromX→e.arcSlotX を easeOutCubic で
// e.y の進捗(0→1)に応じて x に反映するだけ。着地後は homeX(=slotX)基準の
// 従来の挙動にそのまま戻る。
```

**重要な学び（バランス確認の落とし穴）**: 最初はオフスクリーン（画面端の外）から
大きく弧を描く演出で実装したところ、`t_bal.cjs` のオートパイロットが
「一番近いy距離の敵のx」へ自機を寄せるロジックを使っているため、入場中の敵のxが
動くこと自体が自機の移動先を揺らし、中盤NORMALの到達ステージが 3→2 に落ちる
ケースが発生した。調べる過程で **`t_bal.cjs` は完全な決定論ではなく、同じコードでも
試行ごとに frames/score/到達ステージがそれなりにブレる**ことも判明した
（Math.randomを使う敵の細かい挙動やドロップ等が影響している）。
この学びを踏まえ、オフセットを ±90px に抑えて3回試行したところ、
中盤NORMALは毎回ステージ3到達、フル強化NORMALも毎回クリア（またはフレーム上限到達）
となり、無変更時のブレ幅に収まることを確認した。

**教訓**: 敵の入場演出で x 座標を動かす変更は、見た目だけでなく
`t_bal.cjs` のオートパイロットの追従先にも影響する。今後 x を動かす演出を追加する時は
複数回 `t_bal.cjs` を回して「無変更時のブレ幅に収まっているか」で判断すること
（1回の比較だけでは判断を誤る）。

### I15 編隊の形状バリエーション v2.8（deployed）

`formationRow()`（直線隊列）に加えて、**V字（谷型）** `formationV()` と
**くさび形（山型）** `formationWedge()` を追加。x方向のスロット配置・弧入場ロジックは
`formationRow()` と共通のまま、着地y座標だけをスロット位置に応じてずらす
（中心が浅い/深い、両端がその逆）ことで、隊列の見た目にバリエーションを持たせた。
3ステージにそれぞれ1箇所ずつ（stage0=turret、stage1=prism、stage2=bomber）採用。

**重要な発見（このイテレーションでの学び）**: 敵種によって「着地」の実装方法が違うため、
`arcFromX`/`targetY` を使った演出フックが**効かない敵種がある**ことが分かった。
`updateEnemy()` の冒頭で入れている弧演出フック（`!e.entered` の間だけ x を上書き）は、
`grunt`/`turret`/`bomber`/`sniper`/`shield`/`splitter`/`prism`/`carrier` のように
`if(!e.entered){y+=...; if(y>=targetY) enterDone(e);} else {x=homeX+sin(...)}` という
パターンで実装されている敵種にしか効果がない。一方 `weaver`/`orbiter`/`mine`/`mini` は
`entered` フラグを一切立てず常時 x を自前計算で上書きし続ける実装のため、
弧演出フックが**毎フレーム直後に上書きされて完全に無効化される**
（v2.7で `formationRow` に一律で弧演出を入れた際、weaver隊列では見た目上何も変わっていなかった
ことになる。ゲームプレイへの実害はないが、意図した演出が出ていなかった）。
`formationV`/`formationWedge` の第一版は weaver に適用してしまっており、
`targetY` を敵ごとにずらしても weaver 側が完全に無視するため無意味な変更だった。
`t_bal.cjs` を複数回まわした際に見えた中盤NORMALの到達ステージ・生存パターンのブレは、
検証の結果 weaver の挙動とは無関係で、既知の `t_bal.cjs` 非決定性の範囲内と判断した
（無強化/中盤/フル×NORMAL/HARD/NIGHTMAREの9条件×3回を前後で比較、パターンは一致）。
最終的に対象を turret/prism/bomber（entered gating ありの敵種）に絞り直して deploy。

**教訓**: 敵の入場/着地の演出フックを新設する時は、対象の敵種が実際に
「`!e.entered` の間だけ座標を動かし、着地後は別ロジックに切り替わる」実装になっているか
必ず確認すること。`updateEnemy()` の switch-case で敵種ごとに実装パターンが異なるため、
「フックを足したのに見た目が変わらない」場合はサイレントに無効化されている可能性を疑う。

回帰: 通常15本＋`t_bal.cjs`（9条件×3回、後述の非決定性を踏まえて複数回実施）＋`t_smoke2.cjs`
（フルクリア通し）すべてPASS。また回帰スイート内 `t_leak.cjs` の
「初期化でセーブが完全に消える」チェックが `ach:{}` を漏れ扱いにする長年のテスト側の
バグ（実績データ追加時にテストの除外リストが更新されていなかった）に気づいたため、
`up`/`rec` と同様に空オブジェクトなら許容するよう1行修正（ゲーム側のコードは無変更）。

### I16 ボスに新パターン追加 v2.9（deployed）

`bossPatterns()` に新しい弾幕工場関数を2種追加した。

- `fAimSplit(speed)`: 自機を狙う弾を1発撃つ。雑魚プリズムと同じ`split`機構
  （`t>52`で3方向に分裂、ダメージは元の0.85倍）を流用しているだけなので実装コストは低い。
  最初の軌道だけ見て避けても、分裂後の拡散まで見ておかないと追い打ちを食らう。
- `fZigRain(n, speed, amp)`: 上から降る雨が`wave`オプションで左右にジグザグしながら
  落ちてくる。まっすぐ避けても追いつかれるので、うねりのリズムを見て逆方向に動く必要がある。

採用先: boss0(AZURE CRUSHER)最終フェーズに`fAimSplit`、boss1(CRIMSON MOTH)最終フェーズに
`fZigRain`（どちらも既存パターンとの入れ替え）。boss2/中ボス/大ボスは今回変更なし。

**教訓（バランス確認で発見・重要）**: 当初はboss2(GOLD SENTINEL)最終フェーズの
`fAimN(7,0.16,5.6),cd:26,reps:3`（7発の密集スプレッドを3連射）も
`fAimSplit(5.6),cd:26,reps:4`（1発ずつ×4連射、遅れて3方向に分裂）に入れ替えていた。
弾数の総量は近い設計のつもりだったが、`t_bal.cjs`を回すと「フル強化HARDが時間内に
自力クリアする」割合が baseline 1/6 → after 5/6 に跳ね上がった。原因は、
**「見た目の弾数」を揃えても「初速の被弾密度（同時に何発が近接して飛んでくるか）」が
まったく違う**ため。`fAimN`は7発が同時に密集したスプレッドとして飛来し、避けそこねると
複数発をまとめて食らう構造だったのに対し、`fAimSplit`は1発ずつ発射され、分裂も52フレーム
後に時間差で起きるため、実質的に「常に1〜3発がバラけて飛んでくる」形になり、
瞬間的な被弾リスクが大きく下がっていた。この差が`t_bal.cjs`の「stage到達3」バケット
（＝boss2と戦う条件）に集中して出たため、boss2側は元の`fAimN`へ差し戻し、`fAimSplit`は
到達判定に影響しにくい早い段階のボス（boss0）に絞って採用し直した。
中盤NORMAL・フルNORMALの各バケットは前後で完全に一致することを確認済み
（`t_bal.cjs`を合計9回以上、フルHARDのみ差し戻し後に6回追加実行）。

**教訓**: ボスの弾幕パターンを新旧入れ替える時は、弾数・ダメージ量だけでなく
「1回の発射でどれだけの弾が同時に・近い場所に集中するか（瞬間密度）」を揃えないと、
見た目の派手さと裏腹に体感難度が大きく変わることがある。特に「1発が後から分裂する」
系の新パターンは、初速の密度が下がりやすいので注意。

回帰: 通常15本＋`t_bal.cjs`（9条件×複数回、疑わしい差分は追加検証）＋`t_smoke2.cjs`
（フルクリア通し）すべてPASS。

### I17 GOLD SENTINELへの新パターン再挑戦 v2.10（deployed）

v2.9で見送った「GOLD SENTINEL最終フェーズへのfAimSplit採用」に、瞬間密度の問題を
解消した設計で再挑戦した。`fAimSplit(speed, n, spread)` に第2・第3引数を追加し、
`fAimN` と同じ密集スプレッドを同時発射できるように拡張（既存の単発呼び出し
`fAimSplit(5.4)` はn省略時デフォルト1発のまま動くので後方互換）。

```js
// boss0 (AZURE CRUSHER, v2.9のまま): fAimSplit(5.4)          … 単発×3連射
// boss2 (GOLD SENTINEL, 今回差し替え): fAimSplit(5.6,7,0.16) … 元のfAimN(7,0.16,5.6)と
//   全く同じ「7発・0.16rad間隔・速度5.6」の密集スプレッドを同時発射しつつ、
//   52フレーム後に各弾が3方向に分裂する（発射直後の見た目・避け方はfAimNと同一）
```

`t_bal.cjs`で前後比較したところ、中盤NORMAL・フルNORMALの各バケットは完全に一致
（stage到達・死/勝のパターンとも無変更時のブレ幅に収まる）。一方でフルHARDは
baseline（9回: 勝4/フレーム上限生存5/死0）に対しcandidate（9回: 勝3/フレーム上限生存4/死2）
とやや厳しめに振れ、まれに死亡するケースが新たに出現した。これは「発射直後の密度は
揃えたが、52フレーム後に元の弾がそのまま3倍に増える」ため、総弾数はfAimNより多く
なる設計上の帰結。NORMALには一切影響がなく、HARD/NIGHTMAREは「上級者向けを
別途追加」の対象として難度が多少上下すること自体は許容範囲と判断し、この形で採用した。
フルNIGHTMAREは元から毎回死亡する設計のため体感上の変化はない。

**教訓（v2.9からの続き）**: 「瞬間密度」を揃えるだけでは、時間差で増える系の弾幕
（分裂・増殖）は総弾数の面でオリジナルより脅威が増しやすい。発射直後の見た目を
揃える設計変更は「初見の回避難度」は揃えられるが、「その後の総弾量」まで揃えたい
場合は分裂後のダメージ・弾数を減らす（今回はdmgを0.85倍に抑える機構をそのまま
流用済み）などの追加調整も検討要。今回はHARD以上の難度上昇を許容する判断としたが、
もし今後NORMALにも同種の変更を入れる場合は同じ観点でより厳密に検証すること。

回帰: 通常15本＋`t_bal.cjs`（NORMAL/HARD/NIGHTMAREの主要バケットで前後合計20回以上）
＋`t_smoke2.cjs`（フルクリア通し）すべてPASS。

### 検討したが見送り: 隊列形状バリエーションの他敵種への展開（v2.11候補）

I15で導入した`formationV`/`formationWedge`をgrunt/sniper/shieldにも展開しようとし、
3ステージに2箇所ずつ・計6箇所を追加した候補を作って`t_bal.cjs`で検証したところ、
**中盤NORMALが「stage到達3」に至る割合がbaseline 2/6→candidate 6/6に急増**した
（常にstage2止まりだったのが、ほぼ毎回stage3まで進むようになった）。既存の3箇所
（turret/prism/bomber、v2.8で導入・検証済み）だけの状態には無かった、明確でサンプル間の
ブレでは説明しづらい差だったため、この6箇所追加は**全て差し戻し**、v2.10の状態
（turret/prism/bomberの3箇所のみ）に戻して据え置いた。

**教訓（ボスの`fAimSplit`と同根の現象）**: `formationV`/`formationWedge`は着地y座標
（`targetY`）を敵ごとにずらすが、各敵は`if(!e.entered){ e.y+=SPEED*dt; if(e.y>=e.targetY)
enterDone(e); }`という降下ロジックのため、**targetYが浅い（小さい）敵ほど早く`entered`に
なり早く撃ち始め、targetYが深い（大きい）敵ほど撃ち始めが遅れる**。つまり隊列の着地
タイミングが縦にバラけることで、本来「全員がほぼ同時に撃ち始める」はずだった編隊の
初撃が時間的に分散し、瞬間的な弾幕密度が下がる。ボスの`fAimSplit`単発版で起きた
「瞬間密度が下がって体感難度が落ちる」のと同じ構造の問題が、敵編隊の着地タイミングでも
起きていた。3箇所程度なら誤差の範囲に収まっていたが、6箇所（＝1ステージあたり4箇所前後）
まとめて追加すると、複数ウェーブで累積してNORMALの進行しやすさが目に見えて変わる
ほどの効果になったとみられる。

**今後この方向で作業する時の指針**:
- 一度に大量の箇所を変更しない。2〜3箇所ずつ追加し、そのたびに`t_bal.cjs`で
  「stage到達バケット」の分布まで確認してからコミットする（勝敗だけでなく到達段階も見る）。
- どうしても着地タイミングのズレが気になるなら、`spread`（現状は既定14px）だけでなく、
  「敵ごとの降下速度を微調整して着地タイミングを揃える」といった対策も検討の余地がある
  （今回は未実装・未検証）。

回帰は通常15本まで実行しPASSしていたが、`t_bal.cjs`でこの差を検出した時点で
デプロイ前に差し戻したため、本番には影響していない。

### I18 勝利画面の実績トースト重なり修正 v2.11（deployed）

「格納庫UI・スコアランクなど細部の見た目調整」の一環でリザルト（勝利）画面を
実機相当のスクリーンショットで確認したところ、**真エンディング（Zランク）到達時に
「星域解放」「真の終幕」の実績が同時解除され、右上の実績トースト2枚が
中央の「MISSION COMPLETE」の文字（特に"N"や"O"のあたり）に重なって見づらくなる**
問題を発見した。実績トースト自体は通常プレイ中のHUDと共通の描画関数
（`drawAchToast()`）で、常に画面右上（`x=VW-w-10, y=150+i*46`）に固定表示される
実装だったため、勝利画面の大きなタイトル文字（y=150〜290あたりを占有）と
座標が重なってしまっていた。

**修正**: `drawAchToast()`内で`Game.state===STATE.WIN`の時だけ、トーストの
基準y座標を`150`→`40`に引き上げ、タイトル文字の帯（背景の暗幕がy=150〜560）に
かからない上部の余白（ネビュラ/星野のみで文字が来ない領域）に退避させた。
通常プレイ中（HUD表示中）の位置は完全に不変。

```js
const topY = (Game.state===STATE.WIN) ? 40 : 150;
const w=214, h=40, x=VW-w-10, y=topY+i*46 - (1-inA)*18;
```

見た目のみの修正でゲーム性・バランス数値には一切影響しないため、`t_bal.cjs`は
実施せず、通常回帰15本＋`t_smoke2.cjs`（フルクリア通し）のみで確認。
Playwrightで実際に2件同時トースト＋Zランク到達を再現したスクリーンショットで
重なりが解消されたことを目視確認済み。

### I19 実績画面が18項目で下部固定ボタンと重なる不具合を修正 v2.12（deployed）

「格納庫UI・スコアランクなど細部の見た目調整」の続きとして、Playwrightで
タイトル/遊び方/実績一覧/格納庫（各武器・難易度タブ）/リザルト/ポーズ/戦闘中HUD
を実機相当のスクリーンショットで一通り確認したところ、**実績一覧画面
（`drawAch()`）で、実績が18個まで増えたことにより一覧の合計高さが画面をはみ出し、
最後の2項目（「三種の武装」「真の終幕」）が下部固定の「戻る」ボタン（y=742）や
画面下端（VH=800）と重なって読めなくなっている**不具合を発見した。

原因は`const rh=38, top=120;`（1行あたりの高さ38px・開始y=120）が実績の項目数を
考慮しない固定値だったこと。18項目 × 38px = 684px を y=120から積み上げると
y=804まで達し、画面高800pxはおろか「戻る」ボタン（y=742〜782）にも食い込む。
実績はこれまで数を増やす前提の設計になっておらず、格納庫UI（v2.6/I13）のような
スクロール対応もされていなかった。

**修正**: 行間の余白比率（`rh-5`＝5pxの隙間）はそのままに、`rh`を`38`→`34`へ
縮小。18項目 × 34px = 612px（y=120〜732）となり、「戻る」ボタン（y=742〜）より
確実に上に収まるようにした。スクロール機構を新設するよりも変更範囲が小さく、
実績の文言・アイコン・条件表示ロジックには一切手を入れていない。

```js
const rh=34, top=120; // (旧: rh=38)
```

見た目のみの修正でゲーム性・バランス数値には一切影響しないため、`t_bal.cjs`は
実施せず、通常回帰15本（全PASS・FAILゼロ）＋`t_smoke2.cjs`のみで確認。修正後の
実績画面をPlaywrightでスクリーンショットし、18項目すべてが「戻る」ボタンに
かからず表示されることを目視確認済み。

**教訓**: 固定行数を前提にした絶対座標レイアウト（今回の実績一覧、以前の格納庫
強化リストv2.6以前）は、後から項目数が増えると静かに画面外・ボタン裏へはみ出す。
今後リストを追加する画面を作る時は、項目数が変わりうる前提でスクロール化するか、
最低でも「行数を増やしても収まるか」を実績を最大まで解除した状態でスクショ確認
してから確定させること。

### I20 初回「限界突破 UNLOCKED」表示とボタンの重なりを修正 v2.13（deployed）

「格納庫UI・スコアランクなど細部の見た目調整」の続きとして、Playwrightで
ゲームオーバー画面（`drawOver()`）のバリエーションをスクリーンショット確認した
ところ、**フル強化でオーバードライブ中に初めて撃墜される瞬間（＝限界突破が
初解放される瞬間）に表示される「★ 限界突破 UNLOCKED ★」の3行バナーの
3行目（y=510）が、その直下にある固定位置のボタン「格納庫へ」（y=500〜546）に
重なって読めなくなる**不具合を発見した。

このバナーは`Game.extUnlocked`（フル強化状態でラスボスに敗れた時だけ`true`に
なる、v20由来の一度きりの演出）の時だけ表示される3行構成（タイトル/説明/補足）
だが、ボタンのy座標は`Game.extUnlocked`の有無にかかわらず常に固定値`500`
だったため、通常時（1行だけの「強化して もう一度挑もう！」）では問題にならず
見過ごされていた。

**修正**: `Game.extUnlocked`が`true`の時だけボタン群（格納庫へ／タイトルへ／
下部ヒント文）をy=500→522へ22pxずらし、3行バナーとの間に十分な余白を確保。
通常時（`false`）のレイアウトはy=500のまま完全に不変。

```js
const by = Game.extUnlocked ? 522 : 500;
drawButton(bx, by,    bw, 46, '格納庫へ',  true, '#6cf'); addBtn(bx,by,   bw,46,'hangar');
drawButton(bx, by+58, bw, 40, 'タイトルへ', true, '#9f8'); addBtn(bx,by+58,bw,40,'title');
ctx.fillText('Enter / タップ で格納庫', VW/2, by+120);
```

見た目のみの修正でゲーム性・バランス数値には一切影響しないため`t_bal.cjs`は
対象外。通常回帰15本（全PASS・FAILゼロ）＋`t_smoke2.cjs`でPASS確認。修正前後の
スクリーンショットで、限界突破初解放時のバナーとボタンの重なりが解消されたこと、
および通常のゲームオーバー画面（`extUnlocked=false`）のレイアウトが一切変わって
いないことの両方を目視確認済み。

**教訓（I19からの続き）**: 条件付きで表示行数が変わるUI（実績一覧の項目数、
今回のextUnlockedバナーの行数）は、「多い方のケース」でスクリーンショット確認
しないと固定座標との衝突を見逃しやすい。以後、条件分岐で表示内容量が変わる画面
を触る時は、両方のケース（多い方・少ない方）を必ずスクリーンショットで比較する。
